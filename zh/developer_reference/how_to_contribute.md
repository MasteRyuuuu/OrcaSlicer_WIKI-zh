# 如何贡献

本页说明怎样才算一个清晰的问题报告（issue），以及审查者对各类拉取请求（PR）的要求。简要版本以及使用 AI 工具的规则，请参见主仓库中的 [CONTRIBUTING.md]({{L1}})。

审查是 PR 合并过程中最慢的环节。一小群审查者利用业余时间处理数百个打开的 PR。如果 PR 提供了他们需要的内容，就会更快得到审查，也更有可能被合并。

关于使用 OrcaSlicer 的问题，请在 [Discord]({{L2}}) 或 [Discussions]({{L3}}) 中提问，而不要在 issue 或 PR 中提问。

## 提交问题报告

清晰的问题报告更容易重现和修复。问题报告表单会要求填写其中的大部分内容。

- **先搜索已有的问题报告**，包括已关闭的。如果问题已经有人报告过，就在那里补充你的细节。
- **检查最新的每夜构建版。** 问题可能已经修复了。
- **每个问题报告只报告一个问题。**
- **附上截图**，即使描述看起来已经很清楚。
- **附上项目文件（`.3mf`）和日志。** 错误报告表单会说明在哪里找到它们。
- **对于功能请求，描述你想解决的问题**，而不只是解决方案。
- **回复尝试重现问题的人提出的疑问。**

## 开始写 PR 之前

- **搜索打开的 PR，而不只是 issue。** 搜索 issue 编号、函数名和你打算修改的文件。PR 常常因为另一个 PR 已经修复了同样的问题而未经合并就被关闭。如果已有相关 PR，请测试它并在那里评论。
- **认领 issue**：在 issue 下评论 `/assign-me`，让其他人知道你正在处理。
- **在分支上工作**，而不要在你复刻仓库的 `main` 上工作。
- **如果这是你的第一个 PR，从小的改动开始**，比如修复一个错误。小的 PR 被合并得更频繁，也更快。
- **不要一次打开很多 PR。** 如果你已经有好几个打开的 PR，请等其中一些被合并后再打开新的。对一个 PR 的审查意见往往也适用于其他 PR。等待期间，可以看看[其他帮忙方式]({{L4}})。

## 每个 PR 都需要的内容

### 保持专注

- **每个 PR 一个主题。** 属于一起的改动放在同一个 PR 中，例如修复及其测试，或者在多处进行的同一修复。不相关的改动（例如重构和新功能）放在不同的 PR 中，以便各自独立审查和批准。
- **不要把一个改动拆成许多小 PR。** 那样审查者不得不把它们重新拼起来，而相互依赖的 PR 很难按正确的顺序合并。
- **不要重新格式化现有代码。** `.clang-format` 用于新文件。在现有文件中，请与改动周围代码的风格保持一致。[AGENTS.md]({{L5}}) 描述了代码风格。差异中夹杂格式化改动时，真正的改动很难找到，`git blame` 也更难使用。
- **不要做无关的修改。** 不要修正你没有改动的代码中的拼写错误、重命名或空白字符。
- **把大型工作拆成一系列 PR**，前提是每一部分都能独立工作并且本身有用。少于 50 行的代码 PR 被合并的频率大约是超过 1,000 行的 PR 的三倍，而且快得多。

### 写一份审查者用得上的描述

使用 [PR 模板]({{L6}})，并保留它的"How to Download Pull Requests Artifacts"链接作为最后一行。测试者会用到这个链接。每份描述都应当回答以下问题。各类 PR 的小节列出了审查者还需要的其他内容。

- **这个改动做了什么，为什么需要它？** 如果它修复了某个 issue，请在描述中写 `Fixes #1234`，这样 PR 合并时 GitHub 会关闭该 issue。对于多个 issue，每个都要重复这个词，例如 `Fixes #1234, fixes #1235`。如果只修复了 issue 的一部分，就只提及 `#1234` 而不写 `Fixes`，让 issue 保持打开。
- **有没有相关的 PR 或 issue？** 如果另一个 PR 涉及同样的代码或错误，请说明你的 PR 有何不同。
- **你是怎么测试的？** 写明操作系统、打印机配置和步骤。如果结果取决于某个模型或设置，请附上项目文件。写明你添加的所有自动化测试。
- **有什么是你无法测试的？** 例如另一个操作系统，或你没有的打印机。这样拥有它的人就可以检查。

把标题和描述写得可以直接用于发布说明。使用简短、平实、不含习语的句子，因为许多审查者把英语当作第二语言来阅读。你自己的英语水平没有问题，使用翻译工具也完全可以。

### 自己编译和测试

- **在打开 PR 之前，在你自己的平台上编译并运行你的改动。** 之后 CI 会在其他平台上编译它。参见[如何编译 OrcaSlicer]({{L7}})。
- **代码可以测试时，添加自动化测试。** 最好的测试在没有你的改动时失败，有你的改动时通过。推送之前请运行测试。参见[测试]({{L8}})和[如何运行测试]({{L9}})。
- 在请求审查之前，**通读你自己的差异**。

## 各类 PR 需要的内容

| PR 类型 | 标签 | 审查者需要看到的内容 |
| --- | --- | --- |
| [错误修复]({{L10}}) | `bug-fix`、`crash` | 原因、修改前后的对比，尽可能附上测试 |
| [安全修复]({{L11}}) | `SECURITY` | 先私下向维护者报告 |
| [新功能或新设置]({{L12}}) | `enhancement`、`QoL` | 用户为什么需要它、它默认关闭、真实的结果 |
| [性能]({{L13}}) | `optimization` | 测量数据，以及输出没有改变的证明 |
| [重构]({{L14}}) | `optimization` | 行为和输出没有改变 |
| [界面改动]({{L15}}) | `UI/UX` | 你测试过的每个平台上修改前后的截图 |
| [打印机配置]({{L16}}) | `profile` | 验证器通过、版本号已提升、真实的打印结果 |
| [翻译]({{L17}}) | `Localization` | 使用了术语表中的术语、占位符未改变 |
| [编译、CI 或依赖]({{L18}}) | `build`、`dependencies` | 你在哪些平台上编译过 |
| [测试]({{L19}}) | `test` | 行为出错时测试会失败 |
| [文档]({{L20}}) | `documentation` | 与当前代码相符 |

### 错误修复

- **先在最新的每夜构建版上重现错误。** 它可能已经修复了。
- **说明错误为什么会发生**，以及你的改动为什么能修复它。不知道原因，审查者就无法评判修复。
- 用 issue 中的步骤或项目文件**展示修改前后的对比**。如果没有 issue，就把步骤写在 PR 中。
- 代码可以测试时，**把 issue 中的步骤变成自动化测试**。参见[测试]({{L21}})。
- **让修复保持局部。** 如果同样的错误也存在于其他地方，在同一个 PR 中一并修复是可以的。对错误周围代码的较大规模改写，请放在单独的 PR 中。
- **对于崩溃**，检查你的修复是否与报告中的崩溃日志或调用栈相符。如果你的修复针对的是其他代码中看起来相似的崩溃，issue 会保持打开。
- **对于回归**，如果能找到，请写明导致它的 PR 或提交。审查者会检查那个改动的目的在你修复之后是否仍然有效。

### 新功能和新设置

- **说明谁需要它**，以及它为他们解决了什么问题。如果其他切片软件有这个功能，请说明 OrcaSlicer 用户为什么也需要它。
- 对于每个新设置，**说明用户应当如何选择数值**，以及 OrcaSlicer 能否自行选择。
- **新行为默认关闭**，除非另有约定。新选项关闭时，现有的输出不能改变。
- **把新设置放在高级或专家模式中**，而不是简单模式中。
- **把每个新设置链接到 wiki。** 把 wiki 页面锚点作为 `append_single_option_line` 的第二个参数传入，并在 wiki 中为该设置编写文档。参见[如何为 wiki 做贡献]({{L22}})。
- 在共用代码中**避免写死的限制**，以及针对某个厂商或打印机型号的特殊情况。把它做成设置项，或从打印机配置中读取。
- **保证旧项目和旧配置仍然可用。** 很多人有我们从未见过的项目文件和配置。
    - 绝不要改变现有设置的含义。请添加新键，并在 `handle_legacy` 中转换旧值。
    - 重命名预设会破坏继承它的用户预设。使用 `renamed_from` 让旧名称继续有效。
- **展示真实的结果。** 对于打印质量，真实打印件的照片最好，因为预览并不能显示一切。对于应用中可以看到的任何内容，请附上截图。
- **大型功能可以拆分。** 先合并一个能工作的第一部分。未完成的部分用选项禁用，或者移到之后的 PR 中。

`QoL` 用于小的易用性改进。请附上修改前后的截图。

### 性能

- 在同一台机器上**测量修改前后的数据**。写明你使用的模型和设置以及测量方法，并把每次测量重复几次。
- **证明输出没有改变。** 比较修改前后的 G-code，或者解释每一处差异。
- **小心共享状态。** 切片代码中有很大一部分使用 TBB 并行运行。

### 重构

- **说明重构能让什么成为可能。**
- **不要改变行为。** 说明你是如何检查的，例如比较修改前后的 G-code。
- **让重构与修复和功能分开**，并让每一步都保持小规模。

### 界面改动

- **尽早贴出修改前后的截图**，并说明你在哪些平台上测试过。审查者往往在阅读代码之前，就根据截图决定是否想要这个改动。Windows、macOS 和 Linux 的表现常常不同。界面代码没有自动化测试，所以截图或简短的录屏就是证据。
- **使用 OrcaSlicer 自己的控件**，例如 `TextInput`、`ComboBox`、`SpinInput`、`CheckBox`、`RadioGroup` 和 `DialogButtons`，让界面在各处看起来都一致。
- **为高 DPI 屏幕缩放尺寸**，并检查你的改动在深色模式下看起来是否正确。
- **把每条消息写成一个可翻译的字符串**并使用占位符，绝不要用拼接的片段。参见 [AGENTS.md]({{L23}}) 中的"Writing translatable strings in the source"。
- **添加 `UI/UX` 标签。** 界面测试者会关注这个标签。任何他们应当试用的改动都要加上它，即使布局没有变化。

[orca-wxwidgets skill]({{L24}}) 中有关于 wxWidgets 在各平台上的 OrcaSlicer 中如何表现的详细说明。

### 打印机配置

请先阅读[如何创建配置文件]({{L25}})。最常见的问题：

- 对于你修改的每个厂商，**提升 `resources/profiles/<Vendor>.json` 中的 `version`**。否则用户收不到你的更新。CI 不检查这一点，所以审查者必须检查。
- 推送之前**运行 `scripts/check_profile.sh`**（或 `.bat`）。
- **继承而不是复制。** 让耗材丝配置基于现有的通用配置或 OrcaFilamentLibrary 配置。只是重复通用数值的厂商耗材丝配置不会被合并，所以请使用厂商的真实数值。
- **保持现有格式。** 配置 JSON 使用制表符缩进。请原地编辑文件，并保持键的顺序。
- **说明你是如何测试的。** 对于只修改配置的 PR，CI 不会编译测试版本，所以请描述你用这份配置切片和打印了什么。

[orca-profiles skill]({{L26}}) 中有关于创建和修改配置，以及修复配置检查失败的说明。

### 翻译

请阅读[本地化与翻译指南]({{L27}})，并对反复出现的术语使用[本地化术语表]({{L28}})。编辑规则见 [AGENTS.md]({{L29}}) 中的"Localization & translations"一节。最重要的几条：

- **只编辑 `msgstr`。** 要修改英文文本，请修改源代码中的字符串，而不是 `.po` 文件。
- **保持每个占位符**（`%s`、`%d`、`%1%`）和每个 `\n` 与 `msgid` 中完全一致。
- **不要重新换行或重新排列**你没有改动的条目。
- **如果你修改了某个术语，就在该语言中所有地方都修改它**，让设置项和它的提示说明使用同一个词。

[orca-translations skill]({{L30}}) 中有用于查找未翻译条目和检查翻译目录的脚本。

### 编译、CI 和依赖

- **说明你在哪些平台上编译过。** CI 并不覆盖每一个本地编译脚本和选项。
- **说明为什么需要新的第三方库。** 在"关于"对话框的版权列表中注明它。如果它需要新的 Linux 系统软件包，请在同一个 PR 中把它添加到 `scripts/linux.d/debian`。
- **对于工作流改动**，先在你复刻仓库的 Actions 中运行该工作流，并在 PR 中附上运行链接。

### 测试

欢迎只包含测试的 PR。[tests/AGENTS.md]({{L31}}) 说明测试应放在哪里以及如何编写，[如何运行测试]({{L32}}) 说明如何编译和运行测试。

- **证明测试会失败。** 破坏它所检查的行为，或者撤销它所针对的修复，确认测试会失败。
- **让测试快速而可靠。** 它们会在每个 PR 上、每个平台上运行，所以缓慢或不稳定的测试会拖慢所有人。

### 文档

- **用户文档位于本 wiki 中**，它有自己的仓库。参见[如何为 wiki 做贡献]({{L33}})。
- **面向开发者的设计文档放在主仓库的 `docs/HLSD/` 中。** 描述设计当前的样子，而不是它如何演变而来的历史。

## 打开 PR 之后

- **添加标签。** 机器人会评论给出说明。回复 `/bot add-label bug-fix`，或用逗号分隔多个标签，例如 `/bot add-label bug-fix, UI/UX`。标签帮助合适的审查者和测试者找到你的 PR。
- **保持开启"Allow edits by maintainers"**，这样审查者可以直接推送小的修复。
- **完成后把 PR 标记为可供审查。** 草稿 PR 不会被合并。
- **把新的提交推送到同一个 PR。** 请不要关闭它再打开一个新的，因为那样审查历史会丢失。
- **审查者评论之后不要强制推送。** 请改为添加新的提交，这样审查者可以看到自上次查看以来改了什么。PR 通常以压缩（squash）方式合并，所以多几个提交没有关系。
- **保持更新。** 通过把 `main` 合并到你的分支来解决合并冲突，让测试者能下载到可以工作的版本。
- **回复每一条审查意见**，包括自动生成的。你不必同意，但请说明理由。
- **阅读评论，而不只看审查状态。** 这里的大多数审查以评论的形式进行，所以即使 PR 没有显示任何批准，也可能已经被认真审查过了。

### CI 检查

修复失败的检查是 PR 的一部分，所以请阅读错误信息。如果卡住了，请在 PR 中提问。

- **clang-tidy 检查"include what you use"。** 为你使用的每个符号包含对应的头文件。由于有预编译头，缺少 include 时本地编译也可能成功。运行 `scripts/run_clang_tidy.sh`（Windows 上为 `scripts\run_clang_tidy.ps1`）来找出它们。参见[如何运行 clang-tidy 检查]({{L34}})。
- **CI 编译把编译器警告当作错误。** 用一种编译器编译没有警告，并不代表其他编译器也没有。
- **如果这是你的第一个 PR**，CI 会等到维护者批准运行。如果审查要求修改，维护者可能会在你推送修改之后才批准运行。

### 等待审查

审查者都是志愿者，第一次回复可能需要一段时间。等待期间，还有[其他帮忙方式]({{L35}})。

审查者可能会要求修改、向你的分支推送修复，或者更倾向于另一种做法，有时是另一个 PR。这是审查的正常部分，维护者自己也会遇到。维护者拥有最终决定权，因为代码合并后由他们继续维护。PR 上的点赞和表情回应不是合并它的理由。

如果你无法继续某个 PR，请在评论中说明。其他人也许能完成它，并注明你的贡献。

### 如果你的 PR 被关闭

我们可能会关闭不符合本指南的 PR。达到要求后，欢迎你重新打开一个新的 PR。参见 CONTRIBUTING.md 中的[如果你的 PR 被关闭]({{L36}})。

## 其他帮忙方式

- **测试打开的 PR。** 对于修改代码的 PR，CI 会编译可供下载的测试版本。参见[下载拉取请求构建产物进行测试]({{L37}})。说明你测试了什么、在哪个操作系统和打印机上测试，以及是否正常。报告某个功能失败与报告它正常工作同样有用。
- **报告错误。** 参见[提交问题报告]({{L38}})。
- **重现错误报告。** 在最新的每夜构建版上确认错误，并附上截图和能重现问题的项目文件（`.3mf`）。
- **审查 PR。** 审查不需要写入权限。阅读改动、试用它，并说明你检查了什么。
- **翻译、配置和 wiki。** 参见[打印机配置]({{L39}})、[翻译]({{L40}})和[如何为 wiki 做贡献]({{L41}})。
