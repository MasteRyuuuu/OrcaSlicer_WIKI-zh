# 本地化与翻译指南

本指南介绍如何为 OrcaSlicer 的翻译做贡献。我们使用 GNUgettext 从项目中提取字符串资源，使用 PoEdit 编辑翻译。

可以在这里下载它们：

- [GNUgettext]({{L1}}) 软件包包含一组工具，用于从源代码中提取字符串并创建翻译目录（Catalog）。
- [PoEdit]({{L2}}) 为翻译者提供了良好的界面。

安装 GNUgettext 之后，建议把 gettext/bin 的路径添加到 PATH 变量中。

GNUgettext 的完整手册见：[{{U1}}]({{L3}})

#### 添加上下文以区分翻译

有些英文单词拼写相同，但根据使用的位置需要不同的翻译。如果没有额外的信息，gettext 会把它们合并成同一个条目，翻译者只能看到一个字符串，无法区分不同的情况。典型的例子：

- 作为**对齐方式**（左/右）的 `"Right"` 与表示**正确**的 `"Right"`。
- 表示**在……内部**的 `"in"` 与作为**英寸**缩写的 `"in"`。

要把它们拆分成各自独立的可翻译条目，请给字符串附加一个**上下文**。上下文不会显示给用户；只有翻译者能看到它，它用来让各条目保持区分。每个支持上下文的宏都以**两个参数**接收字符串及其上下文——上下文**只写一次**：

| 不带上下文 | 带上下文 |
| --- | --- |
| `L("Right")` | `L_CONTEXT("Right", "Alignment")` |
| `_L("Right")` | `_L_CONTEXT("Right", "Alignment")` |
| `_u8L("Right")` | `_u8L_CONTEXT("Right", "Alignment")` |

这种区分与普通宏一一对应：`L_CONTEXT` **只标记**字符串以便提取（用于翻译在其他地方进行的情况，例如现在保存、稍后再翻译的值），而 `_L_CONTEXT` / `_u8L_CONTEXT` 则**标记并在运行时翻译**——分别直接对应 `_L` / `_u8L`。

对于 `"in"` 的例子，你需要给每一处出现都标上与其含义相符的上下文，例如：

{{C2}}

这样在 PoEdit 中，每个条目都会带着它的上下文显示，`Right [Alignment]` 和 `Right [Correct]`（或者 `in [inside]` 和 `in [inches]`）就可以分别翻译。

> [!NOTE]
> 只在字符串确实有歧义时才添加上下文。每个不同的上下文都会产生一个新条目，每种语言都必须单独翻译它，所以凡是含义相同的地方，请复用同样拼写的上下文。

#### 内置网页中的文本

`resources/web` 下的页面，例如首页、设置向导以及插件和预设包对话框，与界面的其余部分使用同一套翻译目录进行翻译。页面本身不包含任何翻译：承载它的 C++ 代码以简短的键列出页面的字符串，并像其他字符串一样用 `_u8L` 标记，应用会在任何页面脚本运行之前，把这张表以 `window.ORCA_UI_STRINGS` 的形式交给页面。

要给页面添加文本：

1. 把键及其英文文本加入宿主的表中：派生自 `WebViewHostDialog` 的对话框中的 `localized_strings()`，或者其宿主传给 `WebViewHostDialog::localized_strings_script()` 的表（例如 `WebViewDialog.cpp` 中的 `home_page_strings()`）。

    {{C3}}

2. 在标记中，用 `data-i18n` 为元素的文本指定键，或用 `data-i18n-title`、`data-i18n-placeholder` 或 `data-i18n-aria-label` 为相应的属性指定键。标记中也要保留英文；在应用之外打开页面时会显示英文。

    {{C4}}

3. 在页面的脚本中，使用 `T(key, fallback, ...args)`；后面的每个参数依次填入下一个 `%s`。对于包含链接的句子，在英文文本中把链接写成 `<a>label</a>`，并用 `AppendTemplate` 构建这个句子，这样译文可以移动链接的位置，并把它与句子的其余部分一起措辞。

页面会加载 `resources/web/include/i18n.js`，它提供 `T`、`AppendTemplate` 和 `TranslatePage`，并在页面标记就绪后调用一次 `TranslatePage()`。

## 翻译原则

后面的规则是机械性的（占位符、空格、单位）。本节讲的是*如何决定一个字符串应该说什么*。这些原则与具体语言无关；它们来自俄语翻译团队的内部准则。

### 本地化，而不是逐字翻译

本地化人员处理的是字符串的*含义*，而不是它的单词。翻译之前，先弄清楚这个字符串实际控制的是什么：它属于哪个功能、出现在界面的什么位置、起什么作用。脱离这些上下文、仅凭查词典得到的术语通常是错的。

### 保持固定格式消息的一致

反复出现的消息形式每次都应以同样的方式表述，让用户无需重新阅读就能认出它们。例如：

- `Failed to connect to <...>` / `Connection to <...> failed` → 在你的语言中使用同一个模板
- `Are you sure you want to <...>?`
- `If expressed as a %, it will be computed over the <...>`

英文原文对同一个意思的措辞常常并不一致。找出这些情况，在你的语言中把它们统一为同一种模式。

### 英文术语有时一词多义——翻译其含义

英文界面经常用一个词表示几个不同的概念，或者省略了你的语言所需要的限定词。请翻译字符串*表达的意思*，而不是它所用的单词。

最明显的例子是 *flow*：英文把它合并成一个词，而大多数语言必须拆分成三个（参见[术语表]({{L8}})）：

| 英文 | 实际含义 |
| --- | --- |
| Flow ratio | 挤出倍率（一个系数） |
| Flow Rate | 材料的吞吐量（mm/s 或 mm³/s） |
| Flow Dynamics | 喷嘴压力补偿（压力提前系数） |

*Extruder* 也同样一词多义——根据字符串的不同，它可能指整个工具头、送丝电机，或者仅仅是喷嘴：

- `High extruder current on filament swap` → 指**送丝电机**的电流，而不是"挤出机"
- `...all extruders must have the same diameter` → 有直径的是**喷嘴**，而不是挤出机
- `...filament retracted inside the hotend before changing hotends` → 指**热端/工具头**的更换

### 在有帮助的地方扩充说明

提示说明和参数描述可以比英文原文*更详细*，这样读者就不必用一门他们可能不会的语言去查资料。把原始描述当作扩展的基础，而不是需要原样复制的规范。

补充背景信息的良好来源有：[OrcaSlicer wiki]({{L9}})、开发者在 GitHub Issues/Discussions 中的回答、Discord 的历史记录，以及源代码中的注释。

> [!IMPORTANT]
> 如果你断定**英文原文是错的**，不要只在你的翻译中悄悄"修正"它。请与其他人确认这一发现，向开发者报告以便修正源字符串，然后再调整本地化内容。

### 简化措辞（"语义优化"）

开源项目中的界面文本通常由开发者编写，所以往往是按算法的逻辑表述的，而不是写给第一次阅读的人。通常可以去掉这些框架性的内容而不损失含义：

> This option determines whether OrcaSlicer should apply the retract reduction on infill.

逐字翻译会保留整个笨拙的句式。但这个字符串本来就是作为*该设置*的提示说明显示的，所以再说一遍两者的关系是多余的：

> Apply the retract reduction on infill.

而且由于用户并不需要知道"retract reduction"是一个单独的后处理步骤，按意图改写能让人第一眼就看明白：

> Disable retractions while printing infill.

其余的细节请在后面的句子中逐步引入，而不要把每个条件都塞进一个句子里。

### 找到平衡

这些原则在实践中会相互冲突：可用的界面宽度、所需的精确度，以及与切片软件通过变量代入的值保持语法一致，都会把你拉向不同的方向。请在它们之间取得平衡，并选择代价最小的折中。目标是让新用户无需在聊天群里提问或翻阅文章，就能自如地使用这个软件。

### 记住读者

使用 OrcaSlicer 的既有专业人士，*也*有家里有一台打印机的普通人。请保留术语表所确定的专业术语，但在字符串允许的范围内尽量平实地使用它们——准确性和第一眼就能读懂同样重要。

## OrcaSlicer 翻译者通用准则

- 我们推荐使用 _PoEdit_ 进行翻译（如上文所述）。它可以帮助你消除大部分标点错误，并会显示"随机"翻译的字符串（如果使用了 fuzzy 参数）。

- 要检查翻译后的文本在界面元素上的效果，就测试一下 :) 如果你使用 _PoEdit_，只需保存文件。此时会生成一个 MO 文件。把它重命名为 OrcaSlicer.mo，就可以运行 OrcaSlicer 了（见上文）。

- 如果你在 OrcaSlicer 的某处看到编码错误（显示乱码而不是 Unicode 字符），请报告它。这很可能不是你的翻译的问题，而是软件中的缺陷。

- 看看翻译后的短语会用在哪些界面元素上。尤其是按钮，务必确定一种译法，不要在括号中写备选译法，因为这会显著增加按钮的宽度，有时是非常不希望看到的：

- 如果你决定使用自动更正或任何批处理工具，输出结果需要非常仔细地校对。它很容易做出严重破坏内容的修改。

- **短语中的任何格式化部分都必须保持不变。** 例如，不要把 `%1%` 改成 `%1 %`，不要把 `%%` 改成 `%`（表示百分号）等等。这会导致应用程序崩溃。HTML 标签也要保留：在 `Click <a>here</a> to install it.` 中，翻译链接文字，并保留其两侧的 `<a>` 和 `</a>`。

- 请注意空格、换行符（\n）和标点符号。**不要添加额外的换行。** 这对参数名称尤其重要。

- 参数的描述中不应包含计量单位。例如，"Enable fan if layer print time is less than ~~n seconds~~"

- 计量单位使用国际单位制。使用"s"而不是"sec"。

- 温度使用单个字符 `℃`（U+2103），与源文本完全一致：保持 `%d℃`，不要改写成 `°C`、`° C` 或 `%d ℃`。在代码中，请在字符串字面量里写作 `℃`。

- 如果短语末尾没有句点，就不要添加。如果有，也不要忘了加上 :)。

- 在整个应用程序中坚持使用相同的术语是很有用的（尤其是"filament"之类的基本术语）。保持一致，否则会让用户感到困惑。常用 OrcaSlicer 术语在各语言中的既定译法（或应保留英文的术语），请参见[翻译术语表]({{L10}})。

## 机器翻译和需要人工审阅的条目

翻译目录中有些条目是由 AI 模型而不是人翻译的。两种翻译者注释（PoEdit 在"给翻译者的注释"面板中显示的 `#` 行）会告诉你是哪些：

- `# AI Translated`——`msgstr` 由模型生成。它是完整、可用的翻译，用户已经能看到，但还没有懂这门语言的人确认过。如果你审阅了这样的条目，无论保留还是重写，都可以删除这条注释；绝不要把它加到你自己写的翻译上。
- `# Needs human review: <reason>`——模型翻译了这个字符串，但无法确定含义或界面措辞是否正确，通常是因为英文脱离上下文时有歧义（"Tile"是动词还是名词？），因为字符串是一个只有在应用中才能看出作用的简短标签，或者因为两个既定术语相互竞争。原因一栏说明需要检查什么。

需要审阅的条目**不会**标记为 `fuzzy`：fuzzy 条目会对用户隐藏，用户就会看到英文，而一个大概正确的翻译通常好过没有翻译。所以"需要审阅"的意思是*已显示，但未经验证*。审阅方法：

1. 找到这些条目：在 `.po` 文件中搜索 `Needs human review`（或在 PoEdit 中按注释筛选）。
2. 阅读原因，然后在 OrcaSlicer 中查看该字符串出现的位置——用你的翻译目录运行一个编译版本（见上面的准则），或者在源代码中找到该字符串，看看它标注的是什么。
3. 如有需要，修正翻译，然后删除 `# Needs human review` 这一行。如果你重写或确认了翻译，也删除 `# AI Translated` 这一行。
